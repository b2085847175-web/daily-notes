## 0. 先用一句话理解本节

上一节学会了发一个请求。但真实业务里的接口是**一个接一个**的：

```text
先登录 -> 再加购物车 -> 再下单
```

问题马上就来了：登录明明成功了，下一个接口却告诉你“你没有登录”。

本节要解决两件事：

```text
第一件：请求之间怎么保持“我是刚才登录的那个人”   -> 会话保持
第二件：怎么从上一个接口的返回里把数据抠出来     -> JSONPath 提取
```

第一件事的关键词是 cookie、session、token；第二件事的关键词是 JSONPath。这两样东西，后面写框架的时候天天都在用。

一句话总结：

```text
会话保持：让第二个请求还是“同一个人”发的
数据提取：把上一个接口返回里的值取出来，留给下一个接口用
```

## 1. 新手先认识 6 个词

### 1.1 会话（Session）

可以理解成“**我和服务器之间的一次对话**”。

你登录之后，服务器要记住“这个人是已经登录过的”，直到你退出。这段时间就是一次会话。

### 1.2 cookie

存在**客户端（浏览器）本地**的一小段数据。

服务器说“给你一个编号”，浏览器就把它存下来，之后每次请求都自动带上，服务器靠它认出你。

```text
存哪里：客户端
谁管理：浏览器自动带
长什么样：PHPSESSID=9jnolnm7osn0hr8pk41bn7cgak
```

### 1.3 session

存在**服务器端**的会话数据。

服务器把“这个人的登录状态”存在自己这边，然后只在 cookie 里放一个 `session_id`。下次请求带来 `session_id`，服务器就能找到对应的会话。

```text
存哪里：服务端
靠什么关联：cookie 里的 session_id
```

### 1.4 token

服务器签发的一串加密字符串（比如 JWT），**客户端自己存着**，每次请求放进请求头带过去。

```text
存哪里：客户端自己保管
怎么带：放在请求头里，例如 token: xxx 或 Authorization: Bearer xxx
特点：不依赖浏览器，App、小程序、前后端分离项目常用
```

### 1.5 鉴权

鉴权就是“**证明你是谁、你有没有权限**”。

上面三个都是鉴权的手段，只是方式不同。

### 1.6 JSONPath

一种“**从 JSON 里按规则找数据**”的表达式写法，专门用来提取返回结果。

```python
jsonpath.jsonpath(data, '$..order_id')   # 提取所有订单号
```

## 2. 整体执行流程

```text
1. 发登录请求
2. 服务端返回：cookie / session_id / token 三者之一
3. 判断是哪种鉴权方式
4. 用对应的方式把身份带上，发下一个请求
5. 拿到返回结果（一段 JSON）
6. 用 JSONPath 把需要的数据提取出来
7. 提到的东西留给下一个接口用
```

对应到代码：

```text
requests.session()          -> 创建一个会话对象
session.post(...)           -> 用这个会话发请求，cookie 自动带上
r.json()                    -> 把返回转成字典
jsonpath.jsonpath(data, 表达式) -> 提取数据，结果永远是列表
```

## 3. 问题现场：requests 每次请求都是独立的

课上原话：

> requests 请求每一次请求，都是独立的，相当于每次打开一个新的浏览器。

这句话非常形象。你用一个全新的浏览器打开商城，它是不知道你刚才登录过的。

我把这件事用代码验证了一下，对比普通请求和 session 请求发出去的 Cookie 头：

```python
import requests

url = 'http://shop-xo.hctestedu.com'

# 普通请求
r1 = requests.Request('GET', url).prepare()
print('普通请求的 Cookie 头   :', r1.headers.get('Cookie'))

# session
s = requests.Session()
s.cookies.set('PHPSESSID', 'abc123xyz')
r2 = s.prepare_request(requests.Request('GET', url))
print('session 请求的 Cookie 头:', r2.headers.get('Cookie'))
```

实测输出：

```text
普通请求的 Cookie 头   : None
session 请求的 Cookie 头: PHPSESSID=abc123xyz
```

差别一目了然：**普通请求什么都没带，session 请求自动带上了 cookie**。

顺便看一下真实的服务器会不会下发 cookie：

```python
resp = requests.get(url, params={'s': 'index/index'})
print('服务端下发的 cookie:', resp.cookies.get_dict())
```

实测输出：

```text
服务端下发的 cookie: {'PHPSESSID': '9jnolnm7osn0hr8pk41bn7cgak'}
```

服务器确实发了 `PHPSESSID`。问题是：**普通请求拿完就丢了**，下一次请求又是空的；而 session 会把它存下来，下次自动带上。

---

## 4. 解决办法：用 session 保持会话

### 4.1 怎么写

```python
import requests

session = requests.session()          # 1. 创建会话对象
r1 = session.post(url, data={...})    # 2. 用它发登录请求
r2 = session.post(url, data={...})    # 3. 再发下一个请求，cookie 自动带上
```

### 4.2 三个要点

```text
session 是 requests 库里的一个类
作用：保持会话状态
用 session 创建对象后，发多个请求会自动关联 cookie、自动传递 cookie
```

### 4.3 补充：session 不是万能的

课上特别补充了一句，这一点很容易踩：

```text
session 只对「session / cookie 鉴权」的接口有效
对「token 鉴权」的接口，session 不会自动带 token，
必须自己把 token 放进请求头：Authorization: Bearer xxx
```

所以你会发现，用 session 去请求一个 token 鉴权的接口，代码照样能跑，但**该加的 token 还得自己加**。session 额外带来的好处是：能保持 cookie、能复用连接。

### 4.4 怎么判断该用哪种

判断方法很简单：**看登录成功返回什么**。

```text
返回 cookie / session_id  -> 用 session
返回 token 字段           -> 手动把 token 放进请求头
```

## 5. cookie / session / token 的区别

### 5.1 三者的对比

| 对比项 | cookie | session | token |
|---|---|---|---|
| 存在哪里 | 客户端（浏览器） | 服务端 | 客户端自己保管 |
| 靠什么关联身份 | 自己就是凭证 | cookie 里的 session_id | 自己就是凭证 |
| 谁自动管理 | 浏览器自动带 | 需要 cookie 配合 | 要自己放进请求头 |
| 状态 | 有状态 | 有状态 | 无状态 |
| 典型场景 | 网页 | 网页 | App、小程序、前后端分离 |

### 5.2 用一句话理解区别

```text
cookie  ：浏览器本地存的小纸条，每次请求自动带上
session ：服务端存的档案，靠小纸条上的编号来查
token   ：服务端签发的通行证，你自己揣着，每次请求亮一下
```

### 5.3 什么时候用哪个

```text
纯网页项目      -> 常用 session / cookie
App、小程序、
前后端分离项目  -> 常用 token
接口自动化测试  -> 两种都要会，看接口返回什么
```

核心区别再强调一遍：

```text
cookie / session 靠浏览器自动管理，是有状态的
token 不依赖浏览器，是无状态的，所以能跨端
```

## 6. jsonpath的使用

### 6.1 目的

提取想要的数据。

接口返回的是一大段 JSON，你只关心其中一两个值（比如 token、订单号），JSONPath 就是用来“精确定位”的。

### 6.2 语法

| 符号 | 名称 | 含义 | 例子 |
|---|---|---|---|
| `$` | 根节点 | 整个数据，从最外层开始 | `$.code` |
| `.` | 下一级 | 一层一层往里取 | `$.data.orders` |
| `..` | 深层查找 | 不管嵌套多深，找所有匹配的 | `$..order_id` |
| `[index]` | 数组下标 | 取第几个，**从 0 开始** | `orders[0]` |
| `[?(@.xxx==值)]` | 条件过滤 | 满足条件的才要 | `[?(@.status=='已完成')]` |

### 6.3 最重要的一个细节

课上原话：

> jsonpath 取到的结果永远是列表，就算只有一个值也是列表，如 `['2026']`，要拿到值需要加 `[0]`。

例子：

```python
year = jsonpath.jsonpath(data, '$..year')[0]   # 拿到的是 '2026'，不是 ['2026']
```

这个细节后面写框架时非常关键，因为：

```text
不加 [0]  -> 得到的是列表，直接拿去当参数用会出错
加了 [0]  -> 得到的是具体的值
```

```text
     │   ├─ items（商品列表：name、price、count）
     │   ├─ pay_amount
     │   └─ status / create_time
     └─ summary（order_count、total_amount、city[北京, 上海]）
```

### 7.2 题目 1 的答案（文件里已经写了）

```python

```

`$..order_id` 会把三个订单号都找出来，取 `[0]` 就得到第一个：

```text

```

### 7.3 剩下 11 道题的答案（我全部跑过）

| 题号 | 题目 | 表达式 | 实测结果 |
|---|---|---|---|
| 2 | 第一个订单的用户名 | `$.data.orders[0].user.name` | `['张三']` |
| 3 | 所有商品名称 | `$..items..name` | `['苹果手机', '手机壳', '蓝牙耳机', '机械键盘', '鼠标', '鼠标垫']` |
| 4 | 所有商品价格 | `$..items..price` | `[5999, 39, 299, 899, 199, 29]` |
| 5 | 所有用户 id | `$..user..id` | `[101, 102, 101]` |
| 6 | 所有出现过的城市 | `$..city` | `['北京', '北京', '上海', ['北京', '上海']]` |
| 7 | 状态为“已完成”的订单 | `$.data.orders[?(@.status=='已完成')]` | 返回那一个完整订单字典 |
| 7b | 只想要“已完成”的订单号 | `$.data.orders[?(@.status=='已完成')].order_id` | `['20260825003']` |
| 8 | 支付金额大于 500 的 pay_amount | `$.data.orders[?(@.pay_amount>500)].pay_amount` | `[6077, 1185]` |
| 9 | 第三个订单里第一个商品的名称 | `$.data.orders[2].items[0].name` | `['机械键盘']` |
| 10 | 张三（id=101）的所有订单号 | `$.data.orders[?(@.user.id==101)].order_id` | `['20260825001', '20260825003']` |
| 11 | vip_level 大于 1 的用户名 | `$.data.orders[?(@.user.vip_level>1)].user.name` | `['张三', '张三']` |
| 12 | 所有订单的 create_time | `$..create_time` | `['2026-08-25 10:30:00', '2026-08-25 11:00:00', '2026-08-24 20:00:00']` |

### 7.4 三个容易踩的坑

**坑一：`$..name` 会把用户名和商品名一起找出来。**

```text
$..name     -> ['张三', '苹果手机', '手机壳', '李四', '蓝牙耳机', '张三', '机械键盘', '鼠标', '鼠标垫']
$..items..name -> ['苹果手机', '手机壳', '蓝牙耳机', '机械键盘', '鼠标', '鼠标垫']
```

因为用户和商品都用了 `name` 这个字段名。想只要商品名，就得先定位到 `items` 再往下找。**`..` 很方便，但用之前要想清楚会不会匹配到不想要的东西。**

**坑二：`$..city` 的结果里混了一个列表。**

```text
$..city -> ['北京', '北京', '上海', ['北京', '上海']]
```

前三个是地址里的城市（字符串），最后一个是 `summary` 里的 `city`，它本身就是个列表，所以整个被当成了一个结果。**`..` 找到的值，类型可能不一样。**

**坑三：条件过滤里的引号。**

```text
$.data.orders[?(@.status=='已完成')]   <- 对
$.data.orders[?(@.status=="已完成")]   <- 双引号也可以
```

比较运算符要写 `==`（两个等号），字符串要加引号。

## 9. 常见报错和排查方法

### 9.1 `ModuleNotFoundError: No module named 'jsonpath'`

没装库：

```powershell
pip install jsonpath
```

注意包名就叫 `jsonpath`，不是 `jsonpath-ng`，导入的时候也是 `import jsonpath`。

### 9.2 `TypeError: list indices must be integers` 或拿到的值和预期不一样

多半是忘了 `jsonpath` 返回的是列表。

```python
result = jsonpath.jsonpath(data, '$.code')   # 得到 [200]
value = result[0]                            # 得到 200
```

### 9.3 `jsonpath.jsonpath()` 返回 `False`

说明表达式没匹配到任何数据。

排查：

- 是不是多写或少写了一层？`$.data.orders` 和 `$.orders` 不一样
- 字段名大小写对不对
- 想要深层查找，是不是该用 `..` 而不是 `.`

### 9.4 `jsonpath` 报语法错误

检查：

```text
条件过滤的括号：[?(@.status=='已完成')]
比较运算符   ：== 不是 =
字符串       ：要加引号
```

### 9.5 下一个接口提示“未登录”

如果用的是 token 鉴权的接口，光用 `session` 是不够的，必须把 token 放进请求头：

```python
headers = {'token': token}
```

排查顺序：

1. 登录返回里到底有没有 token？
2. token 有没有真的取出来（打印看一眼）？
3. 有没有放进请求头？

### 9.6 `session` 用了但登录状态还是丢了

检查是不是新建了好几个 session：

```python
s1 = requests.session()
s1.post(...)          # 在这个会话里登录

s2 = requests.session()
s2.post(...)          # 这是另一个会话，当然没登录
```

一个会话要一直用同一个对象。

## 10. 本节重点记忆

| 名称 | 作用 |
|---|---|
| 请求独立性 | requests 每次请求都是独立的，像新开一个浏览器 |
| `requests.session()` | 创建一个会话对象 |
| `session.post()` | 用会话发请求，cookie 自动带上 |
| cookie | 存客户端，每次请求自动带 |
| session | 存服务端，靠 cookie 里的 session_id 关联 |
| token | 服务端签发，自己存，每次放进请求头 |
| 鉴权方式判断 | 看登录返回：返回 cookie 用 session，返回 token 就手动加请求头 |
| `$` | JSONPath 根节点 |
| `.` | 取下一级 |
| `..` | 深层查找 |
| `[index]` | 数组下标，从 0 开始 |
| `[?(@.xxx==值)]` | 条件过滤 |
| `jsonpath.jsonpath()` | 提取数据，**结果永远是列表** |

两句话总结：

> 会话保持：普通请求之间是陌生人，`session` 让它们变成同一个人。
>
> 数据提取：`jsonpath` 按表达式找值，取出来的永远是列表，要值就加 `[0]`。
