# 第09课 课堂笔记｜接口自动化测试中的断言机制设计与实践（9月1日）

> 本节目标：给框架补上最关键的一块——断言。让代码自己判断“实际结果”和“预期结果”是否一致，而不是靠人肉看返回。同时把断言封装成一套关键字，让 YAML 里一句话就能断言。

## 0. 先用一句话理解本节

前面几节课有个很严重的问题：**用例根本没有“判断对错”的能力**。

课上原话：

> YAML 用例运行后，无论结果如何，pytest 都显示用例成功。

我在第 04 课也验证过这件事：把密码改成错的，用例照样 `PASSED`。因为代码从头到尾只是“把请求发出去、把结果打印出来”，从来没有人告诉 pytest“什么样的结果是失败的”。

本节要补上这块：

```text
让代码帮我们判断「实际结果」和「预期结果」是否一致
```

而且不只是写一个 `assert`，还要把它封装成关键字，这样 YAML 里也能直接写断言。

一句话总结：

```text
没有断言，测试只是“跑了一遍”；有了断言，测试才知道“对不对”
```

## 1. 新手先认识 6 个词

### 1.1 断言（assert）

一句话：**断定某件事是真的**。如果断错了，程序就直接报错停下。

```python
assert 1 == 1        # 成立，继续往下跑
assert 1 == 2        # 不成立，立刻报 AssertionError
```

### 1.2 预期结果

你**期望**接口返回什么。从需求文档、接口文档里来。

```text
登录成功时，msg 应该是“登录成功”
```

### 1.3 实际结果

接口**真实**返回了什么。运行完从响应里提取出来。

```text
实际返回的 msg 是“用户名或密码错误”
```

### 1.4 比较符

判断两者关系的符号：

```text
==  相等
!=  不相等
>   大于
<   小于
>=  大于等于
<=  小于等于
in  包含
```

### 1.5 错误信息

断言失败时想显示的那句话。写不写都行：

```text
写了   -> 失败时显示你写的话，比如“登陆断言失败了”
没写   -> 显示默认拼出来的信息，比如“A == B失败”
```

### 1.6 封装

把常用的逻辑包成一个方法，用的时候一句话调用。本节把断言逻辑封装成了 10 个关键字。

## 2. 整体执行流程

YAML 里的断言也是一个**步骤**，和发请求、提取数据是平级的：

```text
1. 发送请求         -> 拿到响应
2. 提取数据JSON     -> 把 msg 提取到全局变量 my_msg
3. 断言             -> 比较 my_msg 和期望值
4. 不相等           -> 抛异常 -> pytest 显示 FAILED
```

断言关键字内部的动作：

```text
取出 期望结果 / 实际结果 / 比较符 / 断言类型 / 错误信息
  -> 检查比较符是否合法
  -> 按类型把结果转成数字或文本
  -> 用比较符比一下
  -> 不成立就抛异常
```

## 3. 为什么要断言

### 3.1 问题现场

第 04 课的用例里只有这几行：

```python
response = key_func(**step_value)
print(step_name, response.status_code, response.json())
```

它做了两件事：发请求、打印结果。**没有任何判断**。

所以：

```text
接口返回“登录成功” -> pytest 显示 PASSED
接口返回“密码错误” -> pytest 还是显示 PASSED
```

这就是课上说的“需要自己对比结果是不是想要的，靠肉眼判断 + 人为判断”。

### 3.2 自动化的意义

把人肉判断换成代码判断：

```text
预期结果：登录成功
实际结果：用户名或密码错误
-> 两者不一致 -> 用例失败 -> 报告标红
```

这样 CI 上跑几百条用例，一眼就能看出哪条挂了。

### 3.3 为什么还要 “HTTP 200 不等于业务成功”

这一点前面提过，这里再说一次，因为它是断言的动机：

```text
HTTP 200 只代表“服务器收到了请求并给了回应”
业务是否成功，要看返回内容里的 msg / code
```

所以断言断的是**返回内容**，不是状态码。

## 4. assert 的写法

### 4.1 基本语法

```python
assert 预期结果 == 实际结果, "错误时显示的信息"
```

三个部分：

```text
assert         关键字，Python 自带
判断条件       不成立就报错
, "错误信息"   可选，失败时显示这句话
```

### 4.2 六个比较符

```python
assert a == b    # 相等
assert a != b    # 不等于
assert a > b     # 大于
assert a < b     # 小于
assert a >= b    # 大于等于
assert a <= b    # 小于等于
```

### 4.3 错误信息写不写的区别

```python
# 写了：失败时显示自定义信息
assert result == '登录成功', '登陆失败'
# 失败时报：AssertionError: 登陆失败

# 不写：显示默认信息
assert result == '登录成功'
# 失败时报：AssertionError
```

**建议写**。因为默认信息看不出你到底期望什么，自定义信息能省很多排查时间。

### 4.4 断言成功是什么表现

```text
断言成功 -> 用例通过，没有任何提示，继续往下跑
```

这也是为什么断言成功时你会“感觉它没起作用”——它本来就应该是安静的。

## 5. YAML 里怎么写断言

### 5.1 最直白的写法：断言文本

`1_login.yaml` 里被注释掉的那段就是完整写法：

```yaml
#- 断言:
#    操作类型: 断言文本
#    错误信息: "登陆断言失败了"
#    比较符: "=="
#    断言类型: "文本"
#    期望结果: "登录成功"
#    实际结果: "{{my_msg}}"
```

六个参数：

| 参数 | 含义 | 不写会怎样 |
|---|---|---|
| `操作类型` | 调用哪个断言关键字 | 必填 |
| `比较符` | 怎么比 | 默认 `==` |
| `断言类型` | 文本还是数字 | 默认文本 |
| `期望结果` | 你期望的值 | 必填 |
| `实际结果` | 接口实际返回的值 | 必填 |
| `错误信息` | 失败时显示的话 | 默认自动拼一句 |

### 5.2 实际在用的写法：快捷关键字

`1_login.yaml` 里真正打开的是这两段：

```yaml
- 断言:
    操作类型: 断言文本相等
    期望结果: "登录成功"
    实际结果: "{{my_msg}}"

- 断言:
    操作类型: 断言数字相等
    期望结果: 1
    实际结果: 1
```

注意！**用快捷关键字时不需要写“比较符”和“断言类型”**，因为方法名里已经说清楚了（“相等”就是 `==`，“数字”就是按数字比）。

### 5.3 实际结果是怎么来的

看 `1_login.yaml` 的完整步骤顺序：

```yaml
- 发送登陆接口:          # 第一步：发请求
    ...

- 提取响应数据token:      # 第二步：提取 token
    ...

- 提取响应数据msg:        # 第三步：提取 msg
    操作类型: 提取数据JSON
    表达式: $..msg
    下标: 0
    变量名: my_msg

- 断言:                  # 第四步：断言
    操作类型: 断言文本相等
    期望结果: "登录成功"
    实际结果: "{{my_msg}}"
```

注意这个套路：

```text
先用“提取数据JSON”把要断言的值存进全局变量（my_msg）
再用 {{my_msg}} 把它取出来当“实际结果”
```

**为什么要绕这一圈？** 因为断言方法只能拿到 YAML 传进来的参数，而响应内容存在全局变量里，得先提取出来。

### 5.4 购物车用例里的断言

`2_addcard.yaml`：

```yaml
  - 断言:
      操作类型: 断言文本
      比较符: "=="
      断言类型: "文本"
      期望结果: "加入成功"
      实际结果: "{{my_msg}}"
```

这个用的是底层的 `断言文本`，所以要把比较符和断言类型都写上。

## 6. 断言文本：底层方法逐行讲

所有断言关键字最终都会走到这个方法。完整代码：

```python
    @allure.step("断言文本")
    def 断言文本(self,**kwargs):
        #比较器  == !=
        comparators={
            "==":lambda a,b:a==b,
            ">=":lambda a,b:a>=b,
            "<=": lambda a, b: a <= b,
            "!=": lambda a, b: a != b,
            ">": lambda a, b: a > b,
            "<": lambda a, b: a < b,
            "in": lambda a, b: a in b,
        }

        message=kwargs.get("错误信息",None)#用例有没有传错误信息
        operators=kwargs.get("比较符",'==')#用例有没有传比较符  没有传默认==
        compare_type=kwargs.get("断言类型","文本")#用例有没有传断言类型，没有就默认文本

        #判断你传过来的比较符在不在比较器里面，不在就报错
        if operators not in comparators:
            raise Exception(f"没有对应的比较符{operators}")

        #如果你传过来的是数字，把期望结果转成数字
        if compare_type=="数字":
            kwargs["期望结果"]=float(kwargs["期望结果"])
        else:
            kwargs["期望结果"] = str(kwargs["期望结果"])

        if not comparators[operators](kwargs["实际结果"],kwargs["期望结果"]):
            if message:
                raise Exception(message)
            else:
                raise Exception(f"{kwargs['实际结果']} {operators} {kwargs['期望结果']}失败")
```

### 6.1 第一步：准备一个“比较器字典”

```python
comparators={
    "==":lambda a,b:a==b,
    ">": lambda a, b: a > b,
    "in": lambda a, b: a in b,
    ...
}
```

**`lambda` 是什么？** 可以理解成“**没有名字的小函数**”。

```python
f = lambda a, b: a == b
# 等价于
def f(a, b):
    return a == b
```

所以这个字典的意思是：**比较符字符串 → 对应怎么比**。

```text
'==' -> 用 a==b 比
'>'  -> 用 a>b 比
'in' -> 用 a in b 比
```

这么写的好处是：**不用写一堆 if 判断**。加了新比较符，只要在字典里加一行。

### 6.2 第二步：把参数取出来

```python
message=kwargs.get("错误信息",None)
operators=kwargs.get("比较符",'==')
compare_type=kwargs.get("断言类型","文本")
```

三个参数都有默认值：

```text
错误信息  -> 没写就是 None
比较符    -> 没写默认 ==
断言类型  -> 没写默认 文本
```

所以 YAML 里最省事的写法只要给“期望结果”和“实际结果”。

### 6.3 第三步：检查比较符合不合法

```python
if operators not in comparators:
    raise Exception(f"没有对应的比较符{operators}")
```

如果 YAML 里写了字典里没有的比较符，直接报错。实测：

```text
比较符 ===== -> 失败: 没有对应的比较符=====
```

这一步是“**早失败**”：与其默默用错误的逻辑比出一个结果，不如当场报出来。

### 6.4 第四步：按类型转换

```python
if compare_type=="数字":
    kwargs["期望结果"]=float(kwargs["期望结果"])
else:
    kwargs["期望结果"] = str(kwargs["期望结果"])
```

```text
断言类型=数字 -> 期望结果转成 float
其他情况     -> 期望结果转成 str
```

**为什么要转？** 因为 YAML 里写 `期望结果: 1` 读出来是整数 1，写 `期望结果: "1"` 读出来是字符串。统一转一下，能减少类型不一致带来的误判。

### 6.5 第五步：比较，不成立就抛异常

```python
if not comparators[operators](kwargs["实际结果"],kwargs["期望结果"]):
```

这里有三层，从里往外看：

```text
comparators[operators]                    先按比较符取到那个小函数
comparators[operators](实际结果, 期望结果)  用小函数比一下，得到 True/False
if not ...                                 不成立（False）就进判断
```

**注意参数顺序**：传进去的是 `(实际结果, 期望结果)`，也就是 `a=实际结果`、`b=期望结果`。

用 `in` 的时候要特别注意：

```python
"in": lambda a, b: a in b     # a=实际结果，b=期望结果
```

所以“包含”断言的意思是：**实际结果 包含于 期望结果**。反过来写就错了。

实测：

```text
实际"登录成功" in 期望"登录成功啦" -> 通过
实际"失败" in 期望"登录成功"       -> 失败
```

### 6.6 第六步：拼错误信息

```python
if message:
    raise Exception(message)
else:
    raise Exception(f"{kwargs['实际结果']} {operators} {kwargs['期望结果']}失败")
```

```text
YAML 里写了错误信息 -> 报你写的那句
没写               -> 自动拼一句，比如“用户名或密码错误 == 登录成功失败”
```

实测输出：

```text
实际"用户名或密码错误" == 期望"登录成功" -> 失败: 用户名或密码错误 == 登录成功失败
带自定义错误信息                        -> 失败: 登陆断言失败了
```

## 7. 十个断言关键字：为什么只要一个底层方法

除了 `断言文本`，`api_keywords.py` 里还有 9 个方法：

```python
    def 断言文本相等(self,**kwargs):
        kwargs.update({"比较符":"=="})
        self.断言文本(**kwargs)

    def 断言文本不相等(self,**kwargs):
        kwargs.update({"比较符":"!="})
        self.断言文本(**kwargs)

    def 断言文本包含(self, **kwargs):
        kwargs.update({"比较符": "in"})
        self.断言文本(**kwargs)

    def 断言数字相等(self, **kwargs):
        kwargs.update({"比较符": "==","断言类型":"数字"})
        self.断言文本(**kwargs)

    def 断言数字大于(self, **kwargs):
        kwargs.update({"比较符": ">","断言类型":"数字"})
        self.断言文本(**kwargs)
    ...
```

### 7.1 套路只有一个

每个快捷方法都只做两件事：

```text
1. 把自己对应的“比较符”和“断言类型”塞进参数里
2. 调用底层的 断言文本
```

举两个例子：

```python
# 断言文本相等 -> 自动补上 "=="，然后走底层
kwargs.update({"比较符": "=="})

# 断言数字大于 -> 自动补上 ">" 和 "数字"，然后走底层
kwargs.update({"比较符": ">", "断言类型": "数字"})
```

### 7.2 全部 10 个关键字

| 关键字 | 自动补上什么 | 相当于 |
|---|---|---|
| `断言文本` | 无（底层，可自定义） | 万能 |
| `断言文本相等` | `比较符: ==` | 实际 == 期望 |
| `断言文本不相等` | `比较符: !=` | 实际 != 期望 |
| `断言文本包含` | `比较符: in` | 实际 in 期望 |
| `断言数字相等` | `==` + 数字 | 实际 == 期望 |
| `断言数字不等于` | `!=` + 数字 | 实际 != 期望 |
| `断言数字大于` | `>` + 数字 | 实际 > 期望 |
| `断言数字大于等于` | `>=` + 数字 | 实际 >= 期望 |
| `断言数字小于` | `<` + 数字 | 实际 < 期望 |
| `断言数字小于等于` | `<=` + 数字 | 实际 <= 期望 |

### 7.3 为什么值得这么封装

课上讲了理由：

> 优化点：一眼就能看出断言的是「大于 / 等于 / 不等于」还是「数字」。

对比一下 YAML 里两种写法：

```yaml
# 用底层方法：要写一堆参数，容易写错
- 断言:
    操作类型: 断言文本
    比较符: ">="
    断言类型: "数字"
    期望结果: 5
    实际结果: "{{my_count}}"

# 用快捷方法：意图一眼可见
- 断言:
    操作类型: 断言数字大于等于
    期望结果: 5
    实际结果: "{{my_count}}"
```

第二种明显更好读，而且**不可能把比较符写错**，因为根本没让你写。

### 7.4 `kwargs.update()` 是什么

```python
kwargs.update({"比较符": "=="})
```

`update` 是字典的方法，意思是“**把新字典里的键值对合并进来**”。

```python
kwargs = {'期望结果': '登录成功', '实际结果': '登录成功'}
kwargs.update({"比较符": "=="})
# 变成
kwargs = {'期望结果': '登录成功', '实际结果': '登录成功', '比较符': '=='}
```

如果原来的字典里已经有 `比较符`，就会被**覆盖**掉。这一点很重要：用快捷方法时，你自己写的比较符会被忽略，一切以方法名为准。

## 8. 真实运行输出

### 8.1 跑整条用例

```powershell
python -m pytest -v -s HAT/core/TestRunner.py
```

实测输出：

```text
collecting ... collected 2 items
PASSED
PASSED
2 passed in 0.37s
```

两条用例（登录、购物车）都通过了，说明断言全部成立。

### 8.2 断言成功是什么样

断言成功时**什么都不打印**。所以你在日志里看不到“断言通过”这种字样，只能看到最后的 `PASSED`。

这一点新手容易误判：以为“没输出就是没执行”。其实断言本来就该是安静的。

### 8.3 断言失败是什么样

我把各种断言单独跑了一遍，实测结果：

```text
实际"登录成功" == 期望"登录成功"          -> 通过
实际"用户名或密码错误" == 期望"登录成功"    -> 失败: 用户名或密码错误 == 登录成功失败
带自定义错误信息                         -> 失败: 登陆断言失败了
实际"登录成功" in 期望"登录成功啦"         -> 通过
实际"失败" in 期望"登录成功"              -> 失败: 失败 in 登录成功失败
比较符 =====                           -> 失败: 没有对应的比较符=====
```

断言的六种比较符和快捷方法我都验证过一遍：

```text
断言文本相等    -> 通过
断言文本不相等  -> 通过
断言文本包含    -> 通过
断言数字相等    -> 通过
断言数字不等于  -> 通过
断言数字大于    -> 通过
断言数字大于等于 -> 通过
断言数字小于    -> 通过
断言数字小于等于 -> 通过
```

### 8.4 怎么验证断言真的有用

最直观的办法：把 `1_login.yaml` 里的断言改错。

```yaml
- 断言:
    操作类型: 断言文本相等
    期望结果: "登录失败"      # 故意写错
    实际结果: "{{my_msg}}"
```

再跑一次，pytest 就会显示 `FAILED`，并且给出：

```text
登录成功 == 登录失败失败
```

这就说明断言是真的在起作用了。

## 9. 常见报错和排查方法

### 9.1 断言失败了，但用例还是 PASSED

这是最常见的问题。逐条排查：

```text
1. YAML 里断言那一段是不是被注释掉了？（前面有 #）
2. 执行器是不是只 print 了结果，没有调用断言方法？
3. 断言方法里是不是把 raise 写成了 print？（错误被吞掉了）
```

### 9.2 `Exception: 没有对应的比较符=====`

YAML 里的“比较符”写错了。可用的只有：

```text
==  !=  >  <  >=  <=  in
```

注意必须是 `==`（两个等号），写成一个 `=` 会报错。

### 9.3 `Exception: 登录成功 == 登录失败失败`

断言不成立。看这句话的结构：

```text
实际结果  比较符  期望结果  失败
登录成功  ==      登录失败  失败
```

一眼就能看出是期望写错了还是实际不对。

### 9.4 数字断言报 `'>' not supported between instances of 'str' and 'float'`

**这是个真坑，我实测到了。** 看代码：

```python
if compare_type=="数字":
    kwargs["期望结果"]=float(kwargs["期望结果"])
```

它只把**期望结果**转成了浮点数，**实际结果没有转**。

所以当你从响应里提取出来的实际结果是字符串时：

```text
实际"5"(文本) > 期望3  -> 失败: '>' not supported between instances of 'str' and 'float'
```

而相等比较不会报错，只是默默地判定为“不相等”：

```text
期望1(数字) 实际"1"(文本)  -> 失败: 1 == 1.0失败
```

**怎么办？** 从接口提取出来的值大多是字符串，做数字断言时要注意：

```yaml
# 稳妥做法：期望结果也写成字符串，或者先在用例里确认类型
- 断言:
    操作类型: 断言文本相等
    期望结果: "1"
    实际结果: "{{my_count}}"
```

或者先打印一下实际结果的类型：

```python
print(type(实际结果), 实际结果)
```

### 9.5 期望结果和实际结果写反了

用 `in` 比较符时特别容易出错，因为 `in` 有方向：

```text
实际结果 in 期望结果    <- 代码里的顺序
```

所以“断言文本包含”想表达的是“实际结果包含在期望结果里”。写反了就会得到意料之外的结果。

### 9.6 断言失败但错误信息看不懂

给断言加上 `错误信息`：

```yaml
- 断言:
    操作类型: 断言文本
    错误信息: "登录接口返回的 msg 不对，请检查账号密码"
    比较符: "=="
    断言类型: "文本"
    期望结果: "登录成功"
    实际结果: "{{my_msg}}"
```

失败时就会报这句话，比自动拼的信息清楚得多。

## 10. 本节重点记忆

| 名称 | 作用 |
|---|---|
| 断言 | 判断实际结果和预期结果是否一致 |
| `assert 条件, "错误信息"` | Python 自带的断言写法 |
| 预期结果 | 从需求/接口文档来的期望值 |
| 实际结果 | 接口真实返回的值 |
| 比较符 | `== != > < >= <= in` |
| 错误信息 | 失败时显示的话，建议写 |
| `断言文本` | 底层方法，支持自定义比较符和类型 |
| 9 个快捷关键字 | 把比较符和类型固化，YAML 里更好读 |
| `comparators` 字典 | 比较符 → 对应的小函数 |
| `lambda` | 没有名字的小函数 |
| `kwargs.update({...})` | 把参数合并进字典，会覆盖同名键 |
| `断言类型: 数字` | 把期望结果转成 float |
| 断言成功 | 没有任何输出，用例 PASSED |
| 断言失败 | 抛异常，用例 FAILED |

两句话总结：

> 断言的本质：把“预期结果”和“实际结果”比一下，不一样就报错。
>
> 封装的价值：一个底层方法 + 9 个快捷方法，YAML 里一句话就能表达断言意图。

## 11. 新手练习

### 练习 1：故意让断言失败

把 `1_login.yaml` 的期望结果改成 `"登录失败"`，跑一遍看报错，再改回来。

### 练习 2：体验自定义错误信息

在断言里加上：

```yaml
    错误信息: "登录失败了，请检查账号密码"
```

再故意写错期望结果，看报错信息是不是你写的那句。

### 练习 3：把底层写法和快捷写法都试一遍

同一句断言，分别用这两种写法实现，对比 YAML 的可读性：

```yaml
# 底层
- 断言:
    操作类型: 断言文本
    比较符: "=="
    断言类型: "文本"
    期望结果: "登录成功"
    实际结果: "{{my_msg}}"

# 快捷
- 断言:
    操作类型: 断言文本相等
    期望结果: "登录成功"
    实际结果: "{{my_msg}}"
```

### 练习 4：写一个“包含”断言

登录接口返回的 msg 是“登录成功”。试试断言实际结果是不是包含“成功”两个字：

```yaml
- 断言:
    操作类型: 断言文本
    比较符: "in"
    断言类型: "文本"
    期望结果: "登录成功"
    实际结果: "成功"
```

想清楚这里的 `in` 是谁包含谁。

### 练习 5：亲手踩一次类型坑

```yaml
- 断言:
    操作类型: 断言数字大于
    期望结果: 0
    实际结果: "1"
```

跑一遍，看那个 `'str' and 'float'` 的报错。以后遇到就知道是类型问题。
